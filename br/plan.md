# br Implementation Plan

Keep everything modular and easily understandable.

## Scope

Implement only:

```sh
br update
br update --switch

br install vim git vim@7.3
br install vim --no-switch
br install vim --switch

br generations
```

Do not implement standalone build/switch/boot/test commands, generation selection,
rollback, removal, or other package-management functionality. Do not modify any
README.

## Command Semantics

| Command | Behavior |
| --- | --- |
| `br update` | Resolve the latest remote OS flake, build, show an `nvd` diff, and stage for next boot |
| `br update --switch` | Resolve the latest remote OS flake, build, show the diff, and activate immediately |
| `br install ...` | Update `packages.json`, rebuild from the selected pinned OS source, show the diff, and normally switch |
| `br install ... --no-switch` | Edit the package list only; do not build or activate |
| `br install ... --switch` | Explicitly switch immediately, including when an update is pending |
| `br generations` | Read-only listing of installed system generations |

Make `install --switch` and `--no-switch` mutually exclusive.

**Pending-update exception:** After a successful boot-mode update, subsequent
installs default to building and staging from the updated source, not switching
the running system. Print a warning explaining that an OS update is pending and
that `--switch` activates immediately. Preserve this behavior across multiple
installs until the staged generation is booted or an explicit switch succeeds.

## Dependencies

- `clap` with derive support for CLI parsing.
- `serde` and `serde_json` for package entries and persistent source state.
- `indicatif` for spinners and phase progress.
- `anyhow` for contextual errors.
- `tempfile` for atomic writes and temporary build roots.

Prefer synchronous standard-library process execution. Pass command arguments
directly, never through shell interpolation. Use a filesystem lock to serialize
mutating `br` operations.

## Existing Integration Points

- `br/Cargo.toml` and `br/src/main.rs`: current empty application.
- `modules/flake/default.nix`: package outputs, devshell, and NixOS configuration construction.
- `modules/nixos/pkgs/default.nix`: existing `/nix/osconfig/packages.json` consumer.
- `modules/nixos/default.nix`: common module imports.
- `modules/nixos/boot/validation.nix`: existing boot staging and recovery hooks.

The package loader already handles strings and versioned objects with extra
adapter options. Preserve that contract.

## Source State

Default remote:

```text
github:thundertheidiot/brainrotos
```

Default NixOS configuration: `base`.

Persist state separately from `packages.json`, for example
`/nix/osconfig/br-state.json`. Record the selected immutable OS source,
configuration name, and latest pending boot-generation path.

Requirements:

1. Only `br update` resolves and advances the mutable remote reference.
2. Resolve the remote once per update, then build from that exact immutable source.
3. `br install` always builds from the selected immutable source. It must never silently resolve the latest remote.
4. Preserve the selected source with a persistent Nix GC root. JSON containing a store path is not a GC root.
5. Advance selected-source state only after successful staging or switching.
6. Keep the previously selected source usable if an update fails.
7. Record the latest boot-staged generation after successful boot-mode installs.
8. Recognize that the pending generation has booted by comparing its canonical path with `/run/current-system`.
9. Clear pending status after a successful explicit switch.

For first-run installation, expose pinned source metadata inside each new system
generation, such as `/etc/br/source.json`, generated by the flake configuration.
This allows `br install` to initialize from the running OS without fetching latest.
Read running-generation metadata through `/run/current-system/etc/br/source.json`
so a staged or partially activated generation cannot change the baseline.

If neither persistent state nor running-generation metadata exists, fail with
instructions to run `br update`; do not invent an install baseline by fetching
remotely.

Keep source metadata and GC references consistent. Report partial success
explicitly if activation succeeds but state persistence fails.

## Build And Activation Pipeline

Share one pipeline between update and install:

1. Acquire the mutation lock and read validated state.
2. Determine the exact immutable source and effective action.
3. Build `nixosConfigurations.<name>.config.system.build.toplevel`.
4. Use impure evaluation and explicitly provide `brainrotos=/nix/osconfig`.
5. Prevent automatic lockfile modification or dependency-reference updates.
6. Retain temporary GC roots for the source and candidate closure during the operation.
7. Run `nvd diff` against the resolved running system before activation.
8. Activate the exact built closure with `nixos-rebuild-ng --store-path`, using `boot` or `switch`.
9. Commit selected-source and pending-generation state, maintaining its persistent source root.
10. Report whether the generation is active now or staged for next boot.

Do not implement profile manipulation or bootloader management in Rust. Use NixOS
activation tooling so existing boot-validation hooks still execute. Do not mark
an unbooted generation healthy.

Build and diff failures must prevent activation. Activation failures may already
have changed the profile or services; report that accurately rather than claiming
rollback.

## Package Handling

Support:

```json
[
  "vim",
  {"name": "vim", "version": "7.3"}
]
```

Use an untagged Serde enum. Preserve extra versioned-object fields through a
flattened map.

Requirements:

- Parse `name@version`, rejecting empty names or versions.
- Validate all requested packages before changing the file.
- Missing package file means an empty list.
- Invalid existing JSON or entries produce an error without overwriting the file.
- Preserve existing order and adapter options.
- Avoid adding duplicate names/version identities; retain existing options on duplicates.
- Allow plain and versioned entries for the same package, and multiple historical versions.
- Write formatted JSON atomically using a temporary file in the destination directory.
- Preserve appropriate permissions on replacement.
- Keep saved package requests after a failed build; explain that the list changed but activation failed.

`--no-switch` edits only the list and does not change the selected source or
pending-generation state.

## Progress And Privileges

Use spinners for indeterminate work and phase progress for known steps. Do not
fabricate download/build percentages.

Keep build diagnostics visible. Suspend animation around privilege prompts and
diff output. Disable animation for non-terminal output.

Provide explicit privilege handling for package-file writes, persistent GC roots,
state, and activation. Do not run shell-generated commands or trust
caller-controlled executable search paths in elevated execution.

## Generation Listing

Delegate read-only generation discovery to `nixos-rebuild-ng list-generations`,
preferably consuming its structured output.

Display generation number, date, NixOS version, and available current-generation
markers. Clearly distinguish the running generation from the profile-selected
generation where they differ after boot staging.

No selection, deletion, or rollback commands. Future generation actions must
integrate with the existing recovery mechanism.

## Nix Packaging

- Add `pkgs/br.nix` using `rustPlatform.buildRustPackage` and `br/Cargo.lock`.
- Expose `packages.br`.
- Install `br` through the common NixOS configuration.
- Include explicit runtime dependencies for Nix, `nixos-rebuild-ng`, and `nvd`.
- Add Cargo, Rust, rustfmt, and Clippy to the existing devshell.
- Follow repository Nix style: library imports in a top-level `let`, and self-contained module sections where appropriate.
- Do not overwrite unrelated existing worktree changes.

## Verification

Test CLI validation, package parsing, mixed JSON round trips, adapter-option
preservation, duplicates, malformed files, atomic writes, and state transitions.

Use fake external commands to verify:

- Installs never refresh the remote reference.
- Updates resolve once and build/activate the same source and closure.
- Normal installs switch.
- Pending-update installs warn and stage by default.
- Explicit `--switch` overrides pending boot behavior.
- `--no-switch` executes no build or activation commands.
- Failures stop subsequent phases and preserve the appropriate state.
- Booting the latest pending generation restores normal install behavior.

Run rustfmt, Clippy, Cargo tests, and the Nix package build using the flake
devshell. Verify actual update/install activation and boot-validation behavior in
the existing VM, not on the host.
